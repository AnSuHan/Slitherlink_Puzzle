# 제약 전파 계산 로직 — 풀어 설명한 버전

`docs/constraint_lookahead.md` 의 동반 문서. 같은 로직을 처음 읽는 사람도 따라올 수 있도록 "왜 그런지" 와 구체 예시 중심으로 다시 풀어 쓴 것이다.

---

## 0. 모든 추론의 뿌리 — 두 가지 보편 규칙

자동 추론 전체가 결국 이 둘로 환원된다.

**(1) 셀 규칙**
클루 셀의 둘레 변 중 정확히 `num` 개가 그어진다.
→ "active(그어진 수) == num" 이 정답에서 항상 성립.

**(2) 꼭짓점 규칙**
모든 꼭짓점의 차수(그어진 변 수) ∈ {0, 2}.
→ 정답이 "단일 폐곡선" 이라서. 폐곡선은 모든 꼭짓점에서 들어오면 나가야 함(=2), 안 지나가면 0.

차수 1, 3, 4 는 절대 불가. 이 한 줄이 꼭짓점 추론 전부의 근거다.

## 1. 직접 추론 — "지금 이 순간 보드만 보고" 결정 가능한 것

추가 가정 없이, 라이브 보드 상태만으로 즉시 결론이 나오는 케이스. 세 종류뿐이다.

### 1-1. 셀 quota 도달 (num 다 채움)

- **조건:** 셀의 `active == num`, 그런데 미정 변이 남아 있음
- **결론:** 남은 미정 변은 전부 `-1`

**왜?** num 개 다 그었으니 더 그으면 num 초과. 미정으로 남겨둘 이유가 없다.

**예 (Square num=2):** 좌, 위 변이 그어졌고(active=2) 우, 아래가 미정 → 우, 아래 둘 다 -1 확정.

### 1-2. 꼭짓점 분기 금지 (이미 차수 2 도달)

- **조건:** 꼭짓점 `active >= 2`, 미정이 남아 있음
- **결론:** 그 꼭짓점에 붙은 모든 미정 변 → `-1`

**왜?** 차수 2 초과 금지. 추가로 그으면 차수 3 이상 → 위반.

### 1-3. 꼭짓점 데드엔드 (혼자 남은 변)

- **조건:** 꼭짓점 `active == 0`, 미정이 정확히 1개
- **결론:** 그 마지막 미정 변 → `-1`

**왜?** 만약 그 변을 그으면 꼭짓점 차수 1 → 위반(0 또는 2 만 허용). 그러므로 그 변도 그어질 수 없다.

**예:** 꼭짓점에 변 4 개가 모이는데 3 개는 이미 -1, 1 개만 미정 → 그 1 개도 -1 (혼자 그어지면 안 되므로).

### 1-4. fixed-point 반복

한 번 -1 이 추가되면, 그 -1 이 또 다른 1-1 / 1-2 / 1-3 케이스를 만들 수 있다. 예: 1-3 으로 어떤 변이 -1 → 그 변의 반대쪽 꼭짓점에서 또 1-3 트리거.

그래서 "더 이상 변화 없을 때까지" 직접 추론을 반복한다 (fixed-point).

## 2. Look-ahead — "만약 이 변을 그어 보면?" 가설 추론

직접 추론이 멈춰도 보드는 보통 미정 변투성이다. 그 중 일부는 사실 "그어 보면 어딘가에서 모순이 터지는" 변 — 직접 규칙으로는 안 잡히지만, 한 단계만 들어가 보면 잡힌다. 이걸 자동화한 게 look-ahead.

### 2-1. 핵심 아이디어

> 각 미정 변 `e` 에 대해, 만약 `e=1` 이라고 가정하면, 직접 추론을 끝까지 돌렸을 때 모순이 나오는가?
> - 모순이면 → `e` 는 절대 그어질 수 없음 → 영구 `-1`.
> - 모순이 안 나면 → 결정 못 함(현재 정보로는). 다음 변으로 넘어감.

논리학으로는 **귀류법(reductio ad absurdum)**. `e` 를 가정 → 거짓이 도출 → 가정이 거짓 → `e` 는 그어질 수 없다.

### 2-2. 가설 시뮬레이션의 진행

실제 보드를 망가뜨리면 안 되므로 작업 그리드의 **deep copy(snapshot)** 를 만든 뒤 그 위에서 진행한다.

**단계 A**: snapshot 에 `e=1` 세팅
**단계 B**: 가설 안에서 propagation 반복

각 셀에 대해 active, undecided 를 셈:

| 조건 | 행동 |
|---|---|
| `active > num` | **즉시 모순!** (quota 초과) |
| `active + undecided < num` | **즉시 모순!** (남은 변으로 채울 수 없음) |
| `active == num`, `undecided > 0` | 미정 모두 `-1` (직접 1-1 과 동일) |
| `active+undecided == num`, `active < num` | **미정 모두 `1` (force-draw)** |

각 꼭짓점에 대해 active, undecided 를 셈:

| 조건 | 행동 |
|---|---|
| `active > 2` | **즉시 모순!** (차수 초과) |
| `active == 1 && undecided == 0` | **즉시 모순!** (차수 1 고정) |
| `active >= 2 && undecided > 0` | 미정 모두 `-1` |
| `active == 0 && undecided == 1` | 그 1 변 `-1` |
| `active == 1 && undecided == 1` | **그 1 변 `1` (force-draw)** |

**단계 C**: 더 이상 변화 없거나 모순 발견될 때까지 반복.
**단계 D**: snapshot 으로 작업 그리드 복원 → 가설은 흔적 없이 사라짐.
**단계 E**: 모순이었으면 → 실제 보드의 `e` 를 `-1` 영구화. 아니었으면 → 아무것도 안 함.

### 2-3. force-draw 의 역할 (시뮬레이션 안에서만 1)

가설을 깊게 따라가려면 "이 변은 반드시 그어져야 한다" 도 추적해야 한다. 안 그러면 한 단계 더 들어간 모순을 못 잡는다.

**예 (Square num=3, 가설로 한 변 1 추가됨):**
active=2, undecided=1, active+un=3 == num=3
→ 남은 미정도 반드시 1. 시뮬 안에서 1 로 마킹.
→ 그 1 이 인접 꼭짓점에서 또 다른 추론을 트리거 → 결국 모순 검출.

**"왜 영구로 안 그어 주나?"**
이게 매우 중요하다. force-draw 결과를 실제 보드에 그어 주면 사용자가 직접 추론하고 직접 긋는 풀이 경험을 빼앗는다. 자동 풀이가 되어 버린다.
→ force-draw 는 시뮬레이션 종료 시 snapshot 복원으로 흔적 없이 사라진다. 사용자 보드에는 절대 안 남는다.

### 2-4. Outer loop (look-ahead ↔ 직접 추론)

look-ahead 한 바퀴로 새 -1 이 나오면, 그 -1 들이 직접 추론을 또 풀 수 있다. 반대로 직접 추론이 진전되면 look-ahead 가 더 잡을 게 늘어난다.

그래서:

```
repeat (상한 5 회):
  look-ahead 한 바퀴 → 새 -1 있나?
  직접 추론 fixed-point
  변화 없으면 break
```

## 2-5. 사용자 빨강 마킹(-2) 이 propagation 을 망가뜨리지 않게

UI 에는 사용자가 직접 만들 수 있는 음수 마킹이 두 가지 있다.

- **`-2` (빨강)**: 자동 비활성(-1) 변을 탭하면 이 값으로 바뀐다. "이 -1 에 동의 안 함" 표시. 변 자체는 여전히 그어지지 않는다.
- **`-4` (X)**: 사용자가 그어 둔 변을 탭하면 X 로 잠긴다. 사용자가 명시적으로 잠근 변.

문제는 **`-2` 가 propagation 의 hard premise 가 되면 안 된다** 는 점이다.

### 왜 그런가 (1시 방향 cascade 비활성화 사고)

가정: 사용자가 자동 -1 변 `A` 를 탭해 빨강(-2) 으로 마킹.

만약 propagation 이 `-2` 를 그냥 `-1` 처럼 본다면:
- look-ahead 는 다른 미정 변 `B` 에 대해 가설 `B=1` 을 세움.
- 가설 안에서 force-draw 추론이 진행되어 `A=1` 이 도출됨.
- 하지만 working-grid 의 `A` 는 -2 (≈ -1) 로 잠겨 있어 즉시 모순.
- 따라서 `B` 가 영구 -1 로 굳어짐.

이게 사용자 입장에서는 **"빨강 한 번 찍었더니 1시 방향의 또 다른 변까지 비활성화"** 사고로 보인다.

논리적으로도 이상하다. `-2` 는 사용자가 _질문_ 하고 있는 자리이지, 시스템이 새 deduction 의 전제로 삼아도 된다고 동의한 자리가 아니다.

### 처리 절차 — clear / propagate / restore

`applyConstraints` 가 시작될 때:

1. **스냅샷:** 모든 `-2` 위치를 좌표로 기록.
2. **클리어:** `-1` 과 `-2` 를 둘 다 `0` (미정)으로 되돌린다. (`-4` 는 그대로 — 사용자 X 는 hard 잠금.)
3. **propagation:** 직접 추론 + look-ahead 를 평소대로 실행. 이 단계에서 `-2` 가 있던 자리는 그냥 미정 변으로 취급되며, 정당하다면 propagation 이 그 자리를 다시 `-1` 로 도출.
4. **`-2` 복원:** 스냅샷의 각 위치를 다시 본다. 현재 값이 `-1` 이면 `-2` 로 복원, 그 외(0/1+) 면 그대로 둠.

이 절차의 핵심:

- `-2` 는 propagation 동안 보이지 않는다 → 가짜 cascade 모순이 안 생김.
- 사용자의 빨강 마킹은 시각적으로 보존된다 → "빨강이 사라졌다" 는 UX 사고도 없음.
- 만약 사용자가 직전에 다른 변을 그어 `-1` 의 정당성이 사라졌다면, propagation 이 그 자리를 더 이상 `-1` 로 도출하지 않으므로 빨강도 자연히 사라진다 (의미 없는 빨강을 남기지 않음).

### `-4` 는 다르다 — hard disable 로 둠

`-4` (사용자 X) 는 사용자가 명시적으로 잠근 변이므로 propagation 안에서 `-1` 과 동등하게 취급한다. clear 단계에서 건드리지 않는다. 이 자리에서 새 deduction 이 파생되는 건 정상이다 — 사용자가 "여긴 절대 안 그어진다" 고 확정한 자리이므로.

## 3. 사전 일관성 가드 — 이게 없으면 한 탭에 보드 전체 비활성화

### 3-1. 무엇이 문제인가

라이브 보드가 이미 모순 상태(예: num=1 셀에 변 2 개 그려짐)일 때 look-ahead 를 그대로 돌리면:

> 어느 미정 변 `e` 에 가설을 세우든, 시작 시점이 이미 모순이므로 propagation 이 100% 모순으로 끝남
> → 모든 미정 변이 일괄 `-1`
> → 한 번의 입력으로 보드 전체 비활성화 사고.

이건 **"잘못된 가정에서는 무엇이든 도출된다(ex falso quodlibet)"** 의 직접적 결과다.

### 3-2. 해결

look-ahead 진입 전에 라이브 상태가 일관적인지 검사:

- 어느 셀에서 `active > num` ?
- 어느 셀에서 `active + undecided < num` ?
- 어느 꼭짓점에서 `active > 2` ?
- 어느 꼭짓점에서 `active == 1 && undecided == 0` ?

하나라도 걸리면 → look-ahead 패스 자체를 스킵.

직접 추론은 영향 없다. 직접 추론은 사용자 활성 변을 건드리지 않으므로 모순 상태에서도 기존 결정만 다시 검사할 뿐, 폭주하지 않는다.

## 4. Hidden clue 가드 — `num < 0` 셀은 모든 propagator 가 무조건 스킵

난이도 마스킹으로 숫자가 가려진 셀(`num < 0`)은 둘레 변에 어떤 제약도 걸지 않는다. 직접 / look-ahead 모두 이 셀을 만나면 그냥 넘어가야 한다.

**빠뜨리면 어떻게 되나?** `num < 0` 을 `0` 처럼 읽거나 음수 비교가 빗나가면 `active > num` 이 항상 참이 되어 모든 변이 `-1` → 한 탭에 보드 전체 비활성화. 4 도형 모두에서 이 가드가 누락된 자리가 한 군데라도 있으면 사고.

## 5. 전체 흐름 (`applyConstraints` 한 번 호출 시)

1. **`-2` 위치 스냅샷.**
2. **이전 `-1`, `-2` → `0` 클리어** (`-4` 는 그대로). 추론은 항상 "현재 상태" 기준으로 다시.
3. 직접 추론 fixed-point
4. `for laIter in 0..5`:
   - `isStateConsistent()` 아니면 break
   - look-ahead 한 바퀴 (각 미정 변에 대해 가설 시뮬)
   - 새 `-1` 없으면 break
   - 직접 추론 fixed-point
5. **스냅샷의 각 위치를 다시 본다. 현재 값이 `-1` 이면 `-2` 로 복원.**

**호출 시점:** 퍼즐 `init` / `updateEdge` / undo / redo / restart / Square 의 `checkCurrentPath` 끝.

## 6. 도형별 차이는 "데이터 구조뿐"

규칙 자체는 4 도형 동일. 다른 건 변/꼭짓점 incidence 를 어떻게 계산하느냐:

| 도형 | incidence 처리 |
|---|---|
| Square | 2D 좌표 `(vi, vj)` 로 직접 계산 |
| Hexagon | `_buildVertexIncidence` 캐시 |
| Triangle | `_incidentEdges(vr, vi)` |
| Trihex | edge id (vertex pair 인코딩) → `_edgesByVertex` 맵 |

인접 셀 미러링(같은 변이 두 셀에서 공유될 때 양쪽 다 갱신)도 도형별로 처리 방식만 다를 뿐 의미는 동일.
